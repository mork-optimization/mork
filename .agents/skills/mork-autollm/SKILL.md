# Mork AutoLLM

Operate through Mork's API. Mork owns clones, generation, repairs, screening, tuning, comparison, retries, and checkpoints. Requests such as “improve SOTA” authorize campaign work within the established scope; configuration-only requests stop at a validated draft. Preserve prior choices and authorization across follow-ups.

Use [the helper](scripts/mork_autollm.py) for backend discovery/startup, configuration, `campaign`/`screening` lifecycle actions, server-pool `target` commands, `watch`, logs, and diagnostics. Reuse saved IDs; `watch` discovers active work or the latest backend session. Read command `--help` for arguments and the relevant parts of the [AutoLLM guide](../../../docs/features/autollm.md) for setup or recovery, or the [screening guide](../../../docs/features/instance-screening.md) for dataset preparation. If installed separately, resolve these guides in the Mork checkout.

## New campaign

1. Resolve workload location before any workload: **locally or on one or more remote servers over SSH?** Reuse an explicit answer; ask only for missing server IDs, SSH hosts, dedicated workspaces, environments, resource overrides and the selected screening server. Use `execution.ssh.servers` plus `screeningServerId`; a single server is a one-entry pool. Root workers/heap are defaults. Keep local Codex concurrency at `codex.maxConcurrentSessions: 1` unless the user requests more. Keep Codex, authentication, transcripts, and orchestration local. Remote supervisors survive disconnection; local generation and stage advancement wait while the controller is unavailable.
2. Discover the committed baseline, application working directory, build argument array, relative executable artifact, fixed SOTA specification, and full original instance pool. Trials exclude uncommitted edits. Preserve the user's checkout. In a monorepo use the Git root and appropriate module/reactor build. Resolve campaign input paths against the repository.
3. Use capabilities, artifact identity, and workspace to match a backend, rather than HTTP availability or mode alone. Use a fresh workspace for API/checkpoint/runner version 4; historical campaigns remain with their original controller. Preserve unrelated backends. Run target preflight and inspect every prerequisite result; static validation does not establish connectivity. Qualify every target independently and inspect per-target failures. Only the selected screening server needs an isolated selector environment.
4. Prepare or reuse a provenance-matching approved dataset. Inspect saved screening IDs before resuming. Follow the review requirements below; never substitute the raw pool for a missing training index.
5. Merge user choices with backend defaults and save a complete configuration using the helper. Preserve positive worker overrides; automatic workers resolve on the execution host. Screening uses one sequential worker. Tuning duration is `ignoreInitialMillis + intervalDurationMillis`; honor requested comparison limits too.
6. Inspect `/validate`'s `valid` and `errors`. Create and save a draft ID, run its baseline check, and read the actual emitted parameter count. `withinLimit` covers parameter limits; `ready` covers qualification of the full pool. Inspect `failedTargets` even when counts fit. To proceed with a qualified subset, name it explicitly with repeated `campaign start --target ID`; omitted targets are drained. The cap must be below 300; prune while preserving all supplied seeds if needed. Baseline verification includes a rebuild in another checkout path.
7. Show effective trials, repair/pilot limits, tuning and comparison budgets, workers, and workload estimates, including unresolved application time limits. Start the same draft when running is authorized. Dataset approval and start authorization are separate; reuse existing run authorization instead of asking again.

## Dataset review

Use [screening jobs and review artifacts](../../../docs/features/instance-screening.md) on the full original pool with fixed SOTA. Preserve the sequential warmed-worker protocol, inconclusive inputs, and property-based selector. Testing contains **every retained instance, including training**.

Show the completed report, provenance, criteria, exclusions, retained/inconclusive inputs, training/testing membership, and overlap. Obtain explicit agreement before approving the exact reviewed proposal SHA-256. Ask after the concrete report exists. Use published indexes with valid approval and payload hashes. Changed source/executable, SOTA or inputs invalidate approval. The reviewed v3 manifest authorizes `QUALIFIED_SERVER_POOL` reuse: share its frozen indexes only across qualified targets. Screening timing and exclusions remain evidence from the original host; never infer timing equivalence across servers.

## Status, diagnosis, and recovery

Inspect persisted IDs first. The helper’s all-active-trial watch, status and diagnostic commands expose attempts, progress, failure categories, remote identity, and evidence without creating experiments. Backend-maintained session files replace handwritten “latest status” notes.

Use `status --campaign ID --table` for a compact view of every trial, consumed/maximum tuning budget, elapsed time and last synchronization/activity timestamp. Unavailable progress remains unknown and is reported alongside healthy workers; it is never zero consumption. JSON remains the default without `--table`. Budgets are the latest published checkpoints, not inferred live counts. `watch` also retains healthy progress when a trial's progress or activity endpoint is unavailable.

Distinguish process launch, session readiness, observed generation activity, preparation, and tuning. Report observable turns, commands, edits, messages, and available tokens; these are not hidden model iteration totals. Use the readable timeline or bounded cursor logs; native transcripts are archived after attempts finish.

Use `target list/add/drain/resume/remove` for pool changes. An added server qualifies automatically during an active campaign. Drain before removal; busy, unreconciled or unfinished pinned targets cannot be removed. IDs and definitions are immutable. Trials stay pinned to their assigned server through recovery, and failed targets do not block healthy ones. Keep reports grouped by host; do not claim a pooled cross-host ranking.

Infrastructure retries are bounded and spend zero component repairs. Inspect `NEEDS_ATTENTION` and correct its cause before resuming; unknown failures also pause. Preserve framework tests, objectives, validators, dependencies, and frozen evidence. Do not make a trial agent repair the framework. SSH conversations use the controller metadata helper and must not launch independent pilots, tuning, or comparison.

Read `campaign recovery --id ID` or `trial actions --campaign ID --number N` for backend-authoritative eligibility, blocking reasons and effects. When recovery is authorized, `trial resume --campaign ID --number N` resumes only that trial on its original server and saved checkpoints; `target requalify --campaign ID --id SERVER` runs qualification before resuming that server's blocked work. Resume a stopped campaign explicitly first. When the user directs you to end a blocked trial, use `trial fail --campaign ID --number N --reason "..."`; this records a terminal failure and preserves original evidence and seeds. An active qualified, reconciled server can then accept pending work; a drained server remains drained. Do not end a trial merely because it is slow. Eligibility is checked again by each mutation, and uncertain mutation responses must not be replayed automatically.

Logs are bounded by default: `logs --campaign ID --path PATH --tail 500` (also `--lines`) reads the latest lines with a 256 KiB cap. `--follow` starts there and follows UTF-8-safe byte cursors, skipping to a fresh tail after rotation or a large backlog. An explicit `--cursor` reads one 64 KiB page. Full files remain available through the printed artifact download URL. Prefer `diagnose --campaign ID --trial N --output diagnostic.zip` for an individual failure: defaults are 500 lines per log, 16 evidence/log attempts and 8 MiB uncompressed payload, plus a bounded manifest. `--lines`, `--max-files`, `--max-bytes` and `--timeout` set the limits. Read `diagnostic-summary.json` for failure summaries, unavailable evidence and omissions; the archive is not a complete copy of the run.

Rejoin saved SSH job identities after uncertain responses. `WAITING_FOR_REMOTE` does not prove failure; `CANCELLATION_PENDING` does not prove termination. Confirm cancellation and evidence collection before conflicting workloads. Resume through Mork; completed failed trials stay failed. Execution and collection have separate checkpoints: resume retries missing transcript or result collection without repeating a completed generation or workload. Failed transcript collections remain under `collection-failures/`. Regenerate reports without retuning.

Return configuration path, actual status, campaign/screening ID, dashboard URL, and evidence location. Performance claims require saved comparisons, accounting for failed and incomplete trials.
